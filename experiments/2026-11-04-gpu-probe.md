# Native C++ GPU training probe — 4 November 2026

## Question and established result

Can this laptop execute correct, inspectable training from random initialization through a native C++ runtime on its integrated GPU?

**Yes, for the tested FP32 transformer operations.** The C++ executable passed CPU/GPU comparisons of intermediate activations, loss, every parameter gradient, and the first AdamW update. A simple prediction loss decreased, a controlled direct parameter edit produced its expected effect, and model plus optimizer checkpoint recovery reproduced the next update exactly on the same device.

The largest tested model, **151,775,488 parameters**, completed a three-minute measured GPU training run at **719 synthetic tokens/s**, including full gradients and AdamW updates. Minimum sampled available host memory was **1.98 GiB**. This establishes a working configuration, not the absolute maximum or an overnight stability result.

These are disposable probe models. No pretrained weights were downloaded, and no student architecture or educational sequence has been selected. The capacity runs exercise training computation; their repetitive examples do not measure language ability, transfer, or cumulative development.

## Host and backend

- AMD Ryzen 5 6600H, 6 CPU cores / 12 threads; integrated `gfx1035`, 6 compute units from KFD topology.
- 13.87 GiB usable system RAM, shared with graphics. HIP reports 7,445,450,752 bytes (6.93 GiB) total device memory. This is not additional physical memory or a promise that all of it is safely available.
- Ubuntu 26.04.1, kernel `7.0.0-42-generic`; g++ 15.2, CMake 4.2.3, Ninja. AC power; existing CPU governor `powersave`; no power or driver settings changed.
- Project-local AMD stable packages: `torch[device-gfx1035]==2.14.0+rocm10.1.0`, `rocm[devel]==10.1.0`; PyTorch git revision `11ef10939935619f2c723ba326e3808a750a924e`. HIP runtime reports `71626385` (7.16.26385).
- C++20, release build with `-O1 -DNDEBUG`. Numerical kernels are the optimized prebuilt backend libraries. One compilation job limits setup memory use.
- SDK, compiler, headers, and libraries occupy about 8.5 GiB under ignored `build/venv/`. Python supplies package installation, SDK discovery, and optional process supervision; the native executable performs all model computation.

The command sandbox hides `/dev/kfd` and `/dev/dri`; actual GPU runs used authorized host execution. CPU verification runs in the sandbox. A missing GPU is a hard error for `--device cuda`, never a CPU fallback. LibTorch uses the device name `cuda` for ROCm as well.

The first link attempt exposed a missing library search directory for `librocm-openblas.so.0`. Adding the SDK's `lib/host-math/lib` alongside its other library directories resolved linking and standalone loading. No Python runtime wrapper, GPU-target spoof, or custom kernel was required.

## Method and correctness

One C++ model implements learned token/position embeddings, pre-normalized causal self-attention, a 4x GELU feed-forward block, residual paths, final normalization, and an untied output projection. Attention uses explicit matrix multiplications and masked softmax; cross entropy uses log-softmax and gather. There is no dropout or recurrence.

Seed: `20261104`. Parameters, activations, gradients, and AdamW moments use FP32. AdamW: learning rate 0.003, epsilon 1e-5, weight decay 0.01. The epsilon is recorded because near-zero gradient roundoff can otherwise be amplified in a first-update comparison.

Verification copies identical CPU-initialized weights to the GPU and checks finite values plus elementwise tolerance `3e-5 + 3e-4 * abs(reference)`. It compares actual intermediate tensors, gradients, and updated parameters. Changing the final input token must leave earlier outputs unchanged. Adding 0.75 to one output bias must shift exactly that logit, and restoring the bias must restore the output. This is a controlled edit test, not an intelligent repair.

| Verification | Parameters | Largest absolute difference across forward/gradient/update checks | Prediction loss, before → after 40 steps |
|---|---:|---:|---:|
| CPU reference path | 27,872 | 0 | 3.66656 → 0.05617 |
| GPU, width 32 / 2 layers | 27,872 | 7.15e-7 | 3.66656 → 0.05617 |
| GPU, width 256 / 4 layers | 3,320,576 | 2.86e-6 | 5.87275 → 0.0005323 |

All checks passed, including identical next parameter updates after checkpoint reload. Checkpoints preserve model and optimizer state. RNG persistence is not tested: this model has no stochastic layer or randomized data after initialization. Initial weights are reproducible from the recorded configuration and software; checkpoint files are in the run artifacts.

## Capacity measurements

JFT simulation processes were initially active. At the user's request, throughput measurements waited until they had finished. A host process check found none, and subsequent CPU samples showed 84–92% idle before measurement. Normal desktop applications remained open; swap already contained older application pages. These are laptop-session measurements, not an isolated laboratory benchmark.

Unless otherwise stated: batch 4, sequence 128, vocabulary 256 symbols, FP32 full-parameter AdamW, explicit attention, 5 warmup updates, and 2 CPU dispatch threads. Head width is 64 from width 256 upward. Each timed step includes forward, loss, backward, optimizer update, and GPU synchronization. Initialization, warmup, and final validation are outside the reported timed window. Data is already resident on the selected device. Reported tokens are synthetic symbol positions, not a tokenizer-independent language measure.

| Width / layers | Parameters | Timed window | Synthetic tokens/s | Mean update time |
|---|---:|---:|---:|---:|
| 128 / 4 | 873,984 | 15 s | 39,216 | 13.0 ms |
| 256 / 4 | 3,320,576 | 15 s | 18,640 | 27.4 ms |
| 512 / 4 | 12,932,352 | 20 s | 6,734 | 76.0 ms |
| 768 / 6 | 43,006,720 | 20 s | 2,374 | 215.6 ms |
| 1024 / 6 | 76,216,576 | 25 s | 1,533 | 333.9 ms |
| 1024 / 12 | 151,775,488 | 30 s | 766 | 668.0 ms |
| 1024 / 12, sustained | 151,775,488 | 180 s | 719 | 712.2 ms |

At width 512 / 4 layers with the same sequence, batch, and vocabulary, CPU runs measured 1,906 tokens/s with 2 threads and 2,401 tokens/s with 6 threads. The GPU's 6,734 tokens/s was approximately 2.8 times the faster CPU result. CPU runs set both OpenBLAS/OMP thread variables and the native runtime thread count; these are bounded comparisons, not a complete CPU tuning search.

The 512-wide / 4-layer model also passed with sequence length 512 and the same batch/vocabulary: 13,128,960 parameters, 7,608 tokens/s, and 269.2 ms/update over 25 seconds. Four times as many positions per update improved tokens/s while increasing time and memory per update. The larger position embedding accounts for the small parameter-count difference.

The sustained 151.8M run completed 253 measured updates after 5 warmups. Final loss and every final parameter/gradient were finite. Its first quarter averaged 698.9 ms/update and its last quarter 729.8 ms, a 4.4% slowdown. Sampled maximum temperatures were 93°C from the `amdgpu` sensor and 89.1°C from `k10temp`. These observations do not isolate thermal effects from other desktop/power effects. Long-duration cooling and stability remain to be tested before treating this as an unattended continuous-training setup.

Size escalation stopped here to preserve usable desktop headroom. The short 151.8M run left 2.26 GiB available at its sampled minimum; the sustained run left 1.98 GiB. The next contemplated 227.6M configuration would add about 1.13 GiB for parameters, gradients, and AdamW moments alone, exceeding the remaining budget above the 1.5 GiB reserve. No out-of-memory search was attempted.

The supervisor samples host available memory, process RSS, swap use, whole-device VRAM/GTT use, GPU utilization, and CPU/GPU temperatures every 0.5 seconds. It stops its child process at the time limit or below 1.5 GiB available host memory. This reactive guard is not a hard allocation cap; workload increases also use conservative preflight headroom. Whole-device memory includes other applications; RSS alone excludes some GPU allocations. Neither is presented as exact model memory.

FP32 parameters, gradients, and two AdamW moments alone require approximately 16 bytes per parameter. Actual memory also includes activations, allocator reservation, temporary tensors, runtime libraries, and the desktop. This arithmetic is a lower bound, not a capacity result.

## Interpretation and next question

The integrated GPU is a usable native C++ training backend for this project. There is now a measured tradeoff between rapid iterations at tens of millions of parameters and greater capacity at roughly 152M under the tested short-context settings. Which produces the best student must be learned from educational experiments; parameter count alone cannot settle it.

The initial probe did not test mixed precision, activation checkpointing, other optimizers/architectures, or large vocabularies. Longer context and different batching can change both memory and utilization. The next educational experiment can begin with mimicry/prediction while measuring retention and reuse; the next hardware follow-up should examine longer-run temperatures and speed at a chosen operating point.

## Reproduction

The initial package installation used the existing Codex-bundled installer because system Python 3.14 lacks pip/ensurepip. All installed packages remain in the project environment:

```bash
mkdir -p build/tmp runs/gpu-probe-2026-11-04
python3 -m venv --without-pip build/venv
TMPDIR="$PWD/build/tmp" \
  "$HOME/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/bin/python3.12" \
  -m pip --python build/venv install --no-cache-dir pip==26.3
TMPDIR="$PWD/build/tmp" build/venv/bin/python -m pip install --no-cache-dir \
  --index-url https://stable.repo.amd.com/rocm/whl-next/ \
  'torch[device-gfx1035]==2.14.0+rocm10.1.0' 'rocm[devel]==10.1.0'
XDG_CACHE_HOME="$PWD/build/cache" build/venv/bin/rocm-sdk init
bash scripts/build_probe.sh
source scripts/backend_env.sh
```

For an existing installation, only the last two commands are needed to rebuild and configure the shell. The native binary's `--help` lists its options. Choose a fresh output directory for every run:

```bash
python3 scripts/run_probe.py --output runs/my-gpu-check --timeout 180 -- \
  build/native/rnn2_probe verify --device cuda --output runs/my-gpu-check

python3 scripts/run_probe.py --output runs/my-gpu-benchmark --timeout 180 -- \
  build/native/rnn2_probe benchmark --device cuda \
  --width 512 --layers 4 --heads 8 --seq 128 --batch 4 --vocab 256 \
  --steps 10000 --seconds 60 --warmup 5 --output runs/my-gpu-benchmark
```

GPU execution needs host access to the GPU devices. `--device cpu` uses the same executable and model on the CPU. The supervisor is optional: the binary also runs directly after sourcing `backend_env.sh`.
