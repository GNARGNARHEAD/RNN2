# Approximately 20B on one B200: implementation and checkpoint plan

## Decision and objective

Approved direction, 14 November 2026: GNARGNARHEAD selected **approximately 20 billion parameters on one rented NVIDIA B200**, with **persistent cloud storage and separate downloads**. Develop the continuing student from random weights. Use low-precision computation and compressed training state to pursue this target while preserving learning. Actual fit, throughput, and learning quality still require measurement; the target is not a demonstrated result.

The laptop becomes the development, control, and review machine. The same learner resumes across rental sessions. A future 128 GB machine is not a current design constraint. The educational scope remains simple text/symbol mimicry and prediction, no images, with the smallest foundational loop still to be agreed before educational implementation.

**Status:** approved project direction with implementation work ahead. No B200 has been rented, no CUDA training path has been validated here, and no educational student has been trained. Exact architecture and numerical recipes remain candidates requiring validation and design review. The local probe, build target, and ROCm setup have been retired; its [historical findings](archive/2026-11-04-local-gpu-probe.md) retain useful verification questions. An optimum cannot be claimed from memory arithmetic alone.

## Approved operating direction

Use a single C++ student process on the B200 for inference, differentiation, updates, and inspection. Its cloud storage holds full learning checkpoints. The laptop receives small logs, tutor exchanges, evaluation outputs, and requested tensor summaries. Inspection runs beside the model; it does not require downloading every weight.

The working cycle is:

1. Start a B200 instance with the reproducible environment and persistent volume attached.
2. Initialize a disposable probe, or restore the continuing student's last complete checkpoint once education is authorized.
3. Run bounded work; save observations and consistent checkpoints to the persistent volume.
4. Complete and verify the final checkpoint, then release the GPU.
5. Download a full backup independently of GPU rental time, when useful. The next rental reads the cloud checkpoint directly.

Proposed provider: **Runpod Secure Cloud with a standard network volume**. This is a concrete candidate, not a reservation or a requirement to use that vendor. Choose a datacenter that supports both available single-B200 compute and the network-volume S3 API **before** creating the volume. The volume is tied to its datacenter and attaches at Pod creation. A later B200 allocation there is not guaranteed. [Network volumes](https://docs.runpod.io/storage/network-volumes)

Runpod documents direct S3 access to network-volume files **without a running Pod**. No separate CPU transfer machine is required. Its S3 endpoint is another interface to the same volume, not an independent backup. Network volumes survive Pod termination; container disk does not. [S3 API](https://docs.runpod.io/storage/s3-api), [Pod lifecycle](https://docs.runpod.io/pods/manage-pods)

## Numerical implementation path

Build one C++ student runtime for CUDA. Use small disposable configurations of that runtime for numerical validation before scaling toward 20B. The former local probe and its scripts are no longer an active implementation. Carry forward its correctness checks while building CUDA setup, memory-efficient attention, compressed optimizer state, complete learning-state persistence, and cloud recovery. There is currently no runnable B200 target.

The proposed base is a released **CUDA LibTorch build with Blackwell support**, pinned with its compiler ABI, CUDA libraries, driver requirements, and container digest. PyTorch introduced Blackwell support with CUDA 12.8 in version 2.7; an appropriate current released combination must be selected and tested during preparation. A version label or GPU detection alone is insufficient. [C++ installation](https://docs.pytorch.org/cppdocs/installing.html), [Blackwell support](https://pytorch.org/blog/pytorch-2-7/)

Use LibTorch autograd and its scaled-dot-product attention operator first, checking the actual forward and backward backend for the selected shapes. cuDNN also exposes native C++ attention APIs. Add activation recomputation where its measured memory benefit warrants the extra work. Keep detailed activation capture limited to requested samples rather than retaining a complete trace for ordinary training. [cuDNN attention](https://docs.nvidia.com/cudnn/latest/operations/Attention/)

Validate changes separately:

1. Establish a small FP32 reference and a BF16 full-training candidate on identical initialization and batches. Compare forward values, gradients, parameter updates, causality, loss behaviour, and checkpoint continuation with declared tolerances.
2. Introduce compressed optimizer storage while keeping compute precision fixed. A FlashOptim-style representation is a candidate for the larger capacity target. Its official implementation uses Python/PyTorch and Triton; a faithful C++/CUDA implementation is work to be done, not an installed optimizer switch. Avoid temporary full-size FP32 copies that defeat the memory saving. [FlashOptim source](https://github.com/databricks/flashoptim/blob/main/flashoptim/optimizers.py)
3. Evaluate FP8 and then NVFP4 matrix operations against the established reference. Transformer Engine exposes a framework-independent C/C++ core, but the C++ runtime must own differentiation wrappers, scaling state, stochastic-rounding state, tensor layouts, and buffer lifetimes. NVFP4 is more than casting tensors to four bits. [TE C API](https://docs.nvidia.com/deeplearning/transformer-engine/api/c/transformer_engine.html), [NVFP4 recipe](https://docs.nvidia.com/deeplearning/transformer-engine/features/low_precision_training/nvfp4/nvfp4.html)
4. Test the combined recipe before scaling it. FlashOptim-style state compression plus TE NVFP4 in this C++ runtime is not a combination validated by the cited papers. Retain higher precision for operations where it is needed. Use full-parameter updates; gradient release, CPU offload, and rank-restricted optimizer methods are outside the initial candidate.

CPU/GPU checks on tiny models are numerical controls. They do not establish educational quality. Reduced precision must later be checked for retention and subsequent learning as well as immediate loss.

## Evidence supporting the 20B target

The B200 offering has 180 GB GPU memory. Treat actual free bytes and peak allocated/reserved memory as authoritative on the rented machine. Initially allow roughly 30–40 GB for activations, working buffers, inference, and bounded inspection rather than allocating all nominal capacity to persistent training tensors. This is a planning allowance to test, not a guaranteed sufficient reserve. [B200 offering](https://www.runpod.io/gpu-models/b200)

| Evidence | Relevance and limit |
|---|---|
| Compressed full training | COAT compresses Adam moments and activations to FP8. Its 7B full-training benchmark reports 79.3 GB on one H100 at batch 1/context 2,048; separate experiments study pretraining from scratch. This supports investigating compressed training state, but does not validate the proposed 20B runtime. |
| 20B state budget | FlashOptim-style training state is approximately 7.125 bytes/parameter including moment scales: about 142.5 GB at 20B before activations and temporaries. Its quality evidence includes small-model training from scratch and 8B fine-tuning, not 20B from-scratch training. |

Sources: [COAT, section 6 and Table 8](https://arxiv.org/html/2410.19313v3), [FlashOptim](https://arxiv.org/html/2602.23349v1).

NVIDIA's NVFP4 pretraining research retains main weights, accumulated gradients, and optimizer state in FP32. Its compute savings do not alone deliver the compressed-state estimates above. [NVFP4 pretraining](https://arxiv.org/html/2509.25149v1)

Scale the same configurable runtime through intermediate sizes toward approximately 20B. Intermediate cases, potentially including 14B, are validation steps rather than alternate final student targets. Record exact parameter count, vocabulary, context, batch, accumulated positions per update, and every tensor precision. Include likely growth in context and vocabulary; a tiny symbol vocabulary cannot establish fit for every later workload. If evidence makes a target change necessary, document the constraint and discuss it with GNARGNARHEAD. Exact architecture dimensions remain to be agreed.

Measure full forward/backward/update cycles, optimizer allocation after warmup, occasional generation and inspection, checkpoint writes, and cold reloads. Include both short symbolic batches and a longer-context case. Record host RAM, GPU allocated/reserved memory, device free memory, loss/gradient health, update latency, and effective throughput. Select useful capacity using these results and subsequent learning evidence, not peak tensor-core specifications.

## What must survive a session

Save a consistent snapshot after a completed update with no unrecorded gradient accumulation. At that boundary, gradients and temporary activations can be discarded. The full resume package includes:

- Model parameters and persistent buffers; architecture and tokenizer/vocabulary configuration.
- Optimizer moments, quantization scales, correction terms, parameter groups, step counters, and scheduler state.
- CPU/GPU random generators and relevant low-precision scaling/rounding state; loss-scaler state if used.
- Lesson/version, data cursor and sampling state, replay material or immutable references, tutor history and accepted decisions. Record or resolve pending tutor requests so restart does not silently duplicate an interaction.
- Code/environment identifiers, precision recipe, seeds, component sizes, and hashes. Record future persistent recurrent state if such a design is adopted, or explicitly define a valid reset boundary.

Credentials are supplied separately from the checkpoint. Use relative artifact paths and project identity in published records.

Test several subsequent updates against uninterrupted execution after reload. Check same-environment deterministic equivalence where possible; declare numerical tolerances where kernels are nondeterministic. A successful file load is not sufficient evidence of learning continuity.

### Expected checkpoint payloads

All figures below use decimal GB and omit replay, metadata, padding, exceptional higher-precision tensors, and additional persistent buffers. They are estimates, not files produced by this project.

| Saved representation | 20B | Suitable for faithful learning resume? |
|---|---:|---|
| FP32 weights + two 8-bit moments | ~120 GB + scales | With the remaining state listed above |
| FlashOptim-style native compressed state, ~5.125 bytes/parameter | ~102.5 GB | With the remaining state listed above |
| BF16 weights only | 40 GB | No; optimizer and learning history are missing |
| Raw FP4 weights only | 10 GB + scales | No; also discards the authoritative higher-precision update representation |

FlashOptim's native checkpoint retains the compressed moments/scales and weight correction; these savings are not limited to GPU storage. Do not expand those tensors or export only quantized inference weights and call it an equivalent resume checkpoint. [Compressed checkpoint documentation](https://github.com/databricks/flashoptim#compressed-checkpoints), [serialization implementation](https://github.com/databricks/flashoptim/blob/main/flashoptim/optimizers.py)

## Reliable saves and practical downloads

Proposed initial storage is a **500 GB standard network volume**, expandable when measured usage warrants it. Two retained 20B checkpoints plus one new snapshot require approximately 308–370 GB before other artifacts. Keep replay and logs bounded within the remaining capacity; milestone accumulation may justify 1 TB. Prefer a compute host with **256 GB RAM** if available, while still using bounded serialization buffers. These are planning allocations, not hardware requirements.

The save procedure should be simple and explicit:

1. Pause updates at a clean boundary. Stream state with bounded host buffers into a new immutable checkpoint directory. Do not read changing tensors while pretending to save one consistent state, or materialize a second complete model in host RAM.
2. Use approximately **256 MiB chunks** with per-chunk hashes and recorded tensor layout. Write the completion manifest last. A partially written directory is never a valid resume point. For filesystem writes, close and flush files before publishing completion; establish visibility through the S3 path during validation.
3. Verify new checkpoint contents and retain the previous known-good generation. Prove reload continuity before relying on this format; test fresh-instance recovery during the initial infrastructure experiment. Keep at least two complete generations once they exist, and preserve the previous one until its replacement is accepted.
4. Release the B200 after the complete state is on persistent storage. Download directly from the volume by manifest, without a running GPU. Verify each local chunk and skip already verified chunks after interruption. Mark the local backup complete only when all hashes pass.

The provider's S3 API supports direct downloads but has documented recursive-listing limitations, no bucket versioning/object locking, and single-upload limits. A small manifest plus bounded chunks avoids depending on recursive directory discovery or an unverified promise that a particular copy command resumes partial files. The official example downloader deletes remote files after transfer; do not use that behaviour for authoritative checkpoints. [S3 API](https://docs.runpod.io/storage/s3-api)

Two generations on the same volume protect against a bad checkpoint, not loss of the volume. Keep occasional complete backups on an independent local drive or separate storage service. Losing a local internet connection must not end a cloud run or lose its checkpoint. Do not delete the cloud copy merely because a download started or completed.

Full checkpoints are too large to send after each tutor interaction. Transfer small observations frequently and full backups after meaningful milestones or scheduled session boundaries. Choose the periodic cloud checkpoint interval after measuring write cost and acceptable lost work. Do not assume dense weight updates will yield small binary deltas or large lossless-compression savings.

For an illustrative **100 GB** backup, ideal transfer times are:

| Sustained link rate | Ideal elapsed time |
|---|---:|
| 100 Mbps | 2 hours 13 minutes |
| 300 Mbps | 44 minutes |
| 1 Gbps | 13 minutes 20 seconds |

Calculation: bytes × 8 / bits per second. Actual transfers take longer due to overhead and bottlenecks. Use an independent backup destination with room for multiple complete generations; an external drive is a practical candidate. Recheck available capacity before a download. Bounded chunk processing must work without loading the full checkpoint into laptop RAM.

## Tutor responsiveness

The tutor does not need the whole model downloaded. Run requested inspections on the B200 and return selected measurements and examples. Keep the continuing student in one process rather than duplicating a large inference model beside the trainer.

After the foundational lesson and update mechanism are agreed, measure a real cycle: student generation, tutor API latency, applying the accepted teaching response, a learning block, and a small retention check. Record median and slow-cycle times plus GPU idle time. Prepare examples ahead only within the approved teaching scope; attach student/lesson versions to tutor requests so delayed feedback is identifiable. Do not increase repetition indefinitely merely to keep the GPU busy. The cadence remains an experimental choice, not a predetermined seconds-per-review target.

## Work order and evidence gates

1. **Preparation:** build the CUDA environment and backend-appropriate instrumentation for the new student runtime; define the checkpoint manifest and bounded reader/writer. Pin the actual dependencies. Keep one configurable model source serving validation and the eventual student. Validate host-side format, corruption rejection, and interrupted transfers before scaling.
2. **First bounded B200 session:** use a small disposable numerical model to prove native GPU forward/backward/update and full-state save/reload. Terminate and recreate the compute instance, restore from the volume, and verify continuation. Demonstrate a backup download while no GPU is running. Report startup, recovery, and transfer times as well as compute time.
3. **Precision and capacity:** validate optimizer compression and FP8/NVFP4 separately and in combination; then profile progressively toward the approximately 20B target. Include worst measured generation, inspection, and checkpoint peaks. Preserve a reliable reference when a candidate fails. No claim that a large model fits until a complete training/update/save/reload cycle succeeds.
4. **Education:** return to the smallest mimicry/prediction loop and agree inputs, targets, tutor appraisal, and how feedback changes learning. Review the validated numerical candidate before adopting it as the student's runtime. Measure acquisition, retention, and transfer separately. Numerical probe success does not satisfy this educational gate.

The immediate deliverable is the reproducible CUDA runtime and recovery path, validated first with small disposable configurations. No paid rental or installation was performed during this planning and repository realignment.
